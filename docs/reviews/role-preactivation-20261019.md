## Review and decisions (follow-up commits)
- Endpoint: AccountService calls `${url_api}/user/available-account-types`; BE mounts account-management routes at `/api/user` and `/user` behind authenticate + requireActiveUser; response `{ success, data: { activeRole, roles, ownedRoles, ... } }` with `activeRole` a UserRole enum value (read from the DB row). Note: this GET can WRITE (lazy self-heal transaction when roles/profile rows are inconsistent) and joins 4 tables; it is the same call the account menu makes.
- Cost: one extra GET per navigation in client/provider/marketer areas (parents run guards 'always') plus one on a hard load. BE limiter: GET = BROWSE tier, 900/15 min per user and 300/15 min per IP (src/middlewares/rate-limit.middleware.ts); a 429 is therefore possible on a shared IP.
- Failure policy: 401 -> /auth/login; any other failure (network, timeout 4 s, 429, 5xx, 403, 404, malformed body) -> FAIL OPEN (navigation proceeds as before; backend authorization, ROLE_MISMATCH reconcile and the redirect status note still protect). The original behaviour (cancel with a toast) would have left an initial load blank and locked users out whenever this read failed. Timeout lowered from 8 s to 4 s (injectable).
- AuthStore.followRoleChange skips while a navigation is in flight (the guard's own UrlTree redirect) and re-checks after NavigationEnd / Cancel / Error; before, the role-change effect started a duplicate navigation that superseded the guard's redirect (cancelled the read request).
- The sprite preload (BeboAvatarComponent / bebo-loader) is a separate follow-up and is NOT part of this change.
